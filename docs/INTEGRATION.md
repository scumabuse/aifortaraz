# How the website and the AI module work together

The contract is [contract/CONTRACT.md](../contract/CONTRACT.md) (sections 4.1–4.8 below refer to
it); canonical messages are in [contract/examples/](../contract/examples/). This document
describes how the code of both halves implements it on one machine. Paths starting with
`website/` mean `aifortaraz/safety-inspector/`.

## 1. Architecture

```text
                 Browser (operator, projector)
                 |   |                        ^
   REST + /ws/live   |  <img> MJPEG           |  Telegram app (optional)
   (JWT)             |  http://localhost:8001/stream/<camera>.mjpeg
                 v   |                        |
   +---------------------+                    |
   | website frontend    |  Vite :5173 (make dev) or nginx :8080 (make up)
   | React, overlays     |  proxies /api /health /static /ws to :8000
   +----------+----------+                    |
              | /api/v1 (Bearer JWT), /ws/live?token=<JWT>
              v                               |
   +---------------------+   sendPhoto/sendMessage   +-----------------+
   | website backend     |-------------------------->| Telegram Bot API|
   | FastAPI + SQLite    |                           +-----------------+
   | 127.0.0.1:8000      |  snapshots: website/data/snapshots/
   +----------+----------+
        ^     ^      |
        |     |      | config.updated, error  (over /ws/ingest)
  REST  |     | WS   v
  X-API-Key   /ws/ingest?api_key=<key>
  events, heartbeat, stats, GET config   |  detections, heartbeat (frames only with push_frames)
        |     |
   +----+-----+-----------------------------------------------+
   | AI module  `safety-ai run --config configs/demo_integration.yaml`
   |  supervisor: ConfigSync, WsClient, SpoolSender (spool/events.db),
   |              MJPEG :8001 /stream/<camera>.mjpeg, health :9100 /health /metrics
   |  one worker process per camera: capture -> detector -> tracker -> rules -> sinks
   +----+------------------------------------------------------+
        ^
        |  cam-1: data/samples/cam1.mp4 (or webcam 0)   cam-2: data/samples/cam2.mp4
```

The website never analyses video. It receives metadata (detections, events with one snapshot,
heartbeats, minute statistics) and serves the incident workflow; the annotated video goes from the
AI module straight to the browser (contract 4.7, variant "AI serves MJPEG", camera cards with
`stream_type: mjpeg`). The second variant of 4.7 also works: with `backend.push_frames: true` the
AI module sends `frame` messages and the site relays them at `GET /api/v1/stream/{camera_id}.mjpeg`
(the demo configuration keeps `push_frames: false`).

## 2. Ports

| Component | `make dev` / manual | `make up` |
|---|---|---|
| Website backend | 127.0.0.1:8000 | backend:8000 → localhost:8000 |
| Website frontend | Vite :5173 (`--host 0.0.0.0`) | frontend:80 → localhost:8080 |
| AI MJPEG | 0.0.0.0:8001 (`output.expose: true` in the demo config) | ai:8001 → localhost:8001 |
| AI health/metrics | :9100, same bind address as the MJPEG server | ai:9100 → localhost:9100 |
| AI strict mock backend | 127.0.0.1:8010 (`safety-ai mock-backend`, tests only) | not started |

`output.expose` (or `safety-ai run --expose`) binds both AI servers to 0.0.0.0; without it they
listen on 127.0.0.1 only and a browser on another machine cannot load the video.

## 3. Environment variables

One file, the root `.env` (template [.env.example](../.env.example)); `make init` copies it to
`website/.env` and `safety-ai/.env`, `make dev` re-copies it on every start and every
`make restart-ai`, docker compose passes it with `env_file`.

| Variable | Read by | Meaning | Default |
|---|---|---|---|
| `SEED_AI_API_KEY` | website seed (every start) | plaintext of the API key named `ai-module`, stored as SHA-256; empty → random key once (section 7) | generated by `make init` (32 letters/digits) |
| `SAFETY_AI_API_KEY` | AI module | sent as `X-API-Key` and as `?api_key=` of `/ws/ingest` | = `SEED_AI_API_KEY` (`make init`) |
| `SAFETY_AI_BACKEND_URL` | AI module (`backend.url: ${SAFETY_AI_BACKEND_URL:-http://127.0.0.1:8000}`), `make doctor`, `make demo-preset` | website backend base URL | `http://127.0.0.1:8000`; compose sets `http://backend:8000` for the AI |
| `DEMO_MODE` | website seed | `true`: seeds the four demo cameras once per database and the initial value of the demo-mode setting; afterwards the setting in the database wins (Настройки → Демо-режим, `make demo-preset`) | `true` |
| `DEMO_AUTOSTART` | website | runs the mock generator task (detections, heartbeats, statistics, incidents, 30-day history) | `true` |
| `AI_MJPEG_BASE_URL` | website seed, `make demo-preset` | base URL of the AI's MJPEG as seen by the browser; cards of `AI_CAMERAS` get `<base>/stream/<id>.mjpeg` | `http://localhost:8001` |
| `AI_CAMERAS` | website seed, `make demo-preset`, `make doctor`, `make dev` banner | cameras whose video and data come from the AI module; seeded even with `DEMO_MODE=false` as AI-enabled MJPEG cameras | `cam-1,cam-2` |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_IDS` | `make demo-preset` only | stored in the website's notification settings and used for a test message; the backend itself reads its token from the database | empty |
| `TZ` | AI module (`cameras[].timezone: ${TZ:-Asia/Yekaterinburg}`, zone schedules); containers' local time | plant time zone of the AI side; the website shows times in its own setting «Часовой пояс IANA» (seeded `Asia/Yekaterinburg`) | `Asia/Yekaterinburg` |
| `DATABASE_URL` | website | SQLAlchemy URL; a relative SQLite path is resolved against `website/` | `sqlite:///./data/inspector.db` |
| `DATA_DIR` | website | snapshots directory parent | `./data` |
| `JWT_SECRET` | website (mandatory, ≥ 32 characters) | signing key of the browser sessions | generated by `make init` (64 hex) |
| `ACCESS_TOKEN_MINUTES`, `REFRESH_TOKEN_DAYS` | website | session lifetimes | `30`, `7` |
| `CORS_ORIGINS` | website | allowed browser origins | `http://localhost:5173,http://localhost:8080` |
| `DEMO_SEED_INCIDENTS`, `DEMO_SEED_MINUTES` | website (not in the template) | size of the mock history | `360`, `43200` (30 days) |
| `SAFETY_AI_<SECTION>__<KEY>` | AI module | overrides any setting, list items by index: `SAFETY_AI_CAMERAS__0__SOURCE=0`, `SAFETY_AI_MODELS__PPE=ppe_n_latest`, `SAFETY_AI_PROCESSING__TARGET_FPS=6`, `SAFETY_AI_OUTPUT__EXPOSE=true` | none |

Precedence on the AI side: defaults < YAML < `safety-ai/.env` < process environment < CLI flags.

## 4. One violation, step by step

Example: a worker in the cam-1 zone «Пресс №2» (danger zone, required helmet and vest) takes the
helmet off.

1. **Detection.** The cam-1 worker grabs frames at `processing.target_fps` (10), runs the PPE
   model (`models.ppe`, section 10) and the tracker. The model sees a bare `head` in the person's
   head region and no `helmet`, so the helmet evidence is MISSING.
2. **Smoothing and confirmation.** Per track and item `s ← 0.7·s + 0.3·v` (v = −1 for MISSING);
   VIOLATION starts after `confirm_frames` consecutive frames with `s ≤ −0.3`. From a worn helmet
   (s ≈ +1) that is 3 frames to cross plus the confirming frames: about 9 processed frames with
   `confirm_frames = 6`, about 0.9 s at 10 fps. Unknown evidence (nothing visible) never counts as
   missing.
3. **Live state.** Every processed frame, at most 15 per second, the AI sends a `detections`
   message over `/ws/ingest` (contract 4.5, [ws_detections.json](../contract/examples/ws_detections.json)):
   normalized `[x, y, w, h]` boxes, `ppe` only for the items the zone requires (`true`, `false`,
   `null` = unknown), `zones`, `state` `ok` → `violation`. The website keeps the last message per
   camera in memory and forwards it on `/ws/live` to browsers subscribed to `cam-1`; the Live page
   draws the boxes over the MJPEG image (✓/✗/? per item).
4. **Event.** The rule engine starts a `ppe_violation` with
   `external_id = cam-1-<unix_seconds_at_start>-<track_id>-ppe_violation`, `severity: null`,
   `details.missing_ppe = ["helmet"]`, `present_ppe`, `boxes`, `frame_size`
   ([event_ppe_violation.json](../contract/examples/event_ppe_violation.json)) and a raw JPEG
   snapshot (quality 85, longest side ≤ 1280 px). The worker writes it to the spool
   (`spool/events.db`) and `events/<external_id>.jpg` / `.mp4`.
5. **Delivery.** The spool sender posts it as `multipart/form-data` (`payload` + `snapshot`) to
   `POST /api/v1/ingest/events` with `X-API-Key` (contract 4.1). Connection errors, timeouts, 5xx
   and 429 are retried forever with back-off; 401/403 every 10 s; 422 is logged and saved to
   `logs/rejected/` (contract 4.8). The log line reads
   `camera cam-1: POST <external_id> accepted (HTTP 201, backend id <id>, <s> s after enqueue)`.
6. **Website.** The backend validates the payload strictly (422 with `details.fields` on any
   problem), answers 201 `{"id", "status": "new", "severity", "deduplicated": false}`, 200 with
   the same id for a repeated `external_id`, or 202 `{"deduplicated": true, "id"}` when an
   incident of the same camera, zone, type and track started within the zone's `cooldown_sec`
   (else the global one). It resolves the severity (null → zone `severity_override` → type
   default; helmet missing in a danger zone → `high`), stores the snapshot and a 320 px thumbnail
   in `data/snapshots/`, creates the incident with `source = ai`, broadcasts
   `incident.created {incident}` on `/ws/live` (contract 4.6) and queues the Telegram message
   (filters, quiet hours and a 120 s per-camera-and-type cooldown of the notification settings).
7. **Browser.** The incident appears in the journal and on the dashboard with the «AI» badge; the
   incident page draws `details.boxes` on the snapshot.
8. **End.** When the helmet is back (`s ≥ +0.1` for `confirm_frames` frames, then no item in
   VIOLATION for another `confirm_frames` frames) the AI sends
   `PATCH /api/v1/ingest/events/{external_id}` `{"ended_at"}`
   ([patch_end.json](../contract/examples/patch_end.json)); the website computes `duration_sec`
   and broadcasts `incident.updated`. A 404 (the POST never arrived) makes the AI re-POST the event
   with `ended_at`. The same track can trigger again only after `cooldown_sec` (20 s with
   `make demo-preset`).
9. **Alongside.** Every 5 s per camera a heartbeat (`POST /api/v1/ingest/heartbeat` and a WS copy,
   [heartbeat.json](../contract/examples/heartbeat.json)) with `extra.supported_ppe`; every whole
   UTC minute a statistics window (`POST /api/v1/ingest/stats`,
   [stats.json](../contract/examples/stats.json)) from which the dashboard computes the compliance
   KPI of the camera.

## 5. Configuration sync

- **Initial load.** At start the AI's ConfigSync calls `GET /api/v1/ingest/config` (all cameras
  with `ai_enabled`) and `GET /api/v1/ingest/config/{camera_id}` for cameras missing from that
  list ([config.json](../contract/examples/config.json), contract 4.4). A camera that the backend
  cannot provide falls back to `safety-ai/cache/config_<camera>.json`, the last good
  configuration; without either it runs with no zones until the first configuration arrives.
- **Refresh.** Every 60 s, on every `config.updated` message and on every WebSocket (re)connect;
  only changed configurations (version or content) are forwarded to the camera worker, about a
  second later.
- **Push.** The website pushes `{"type": "config.updated", "camera_id", "version"}` to every
  connected `/ws/ingest` client (and to browsers) right after the commit.
- **Version.** One global integer `config_version` for all cameras, incremented by: the zone
  editor save (`PUT /api/v1/cameras/{id}/zones`), `POST /zones`, `PUT /zones/{id}`,
  `DELETE /zones/{id}`, camera create/update/delete and plan moves, thresholds
  (`PUT /api/v1/settings`), general settings, PPE types, incident types and areas. Camera and zone
  changes push `config.updated` for that camera, global changes for every camera.
- **What the AI applies.** Disabled zones are not in the config; null zone `confirm_frames` /
  `cooldown_sec` are filled with the thresholds by the website; schedules are converted from the
  editor's weekdays 0..6 (Monday = 0) to the contract's 1..7 (DECISIONS.md I-009) and evaluated in
  `cameras[].timezone`. The applied version per camera is visible as `config_version` in
  `http://127.0.0.1:9100/health`; the root test `test_config_roundtrip` requires it within 3 s of
  the save.
- With a backend, the website's zones always win, also for `fake:` sources; the YAML's
  `zones_file` entries are used only with `SAFETY_AI_BACKEND__ENABLED=false`.

## 6. Mock switching

- The mock generator (`DEMO_AUTOSTART=true`, demo mode on) animates every enabled camera with
  `ai_enabled = true`: detections 10/s, heartbeats every 5 s, statistics every minute, an incident
  every 20–90 s divided by the intensity, all marked `source: mock` («демо» / «ДЕМО» badges).
- A camera counts as **real** for 60 s after its last real signal: an AI HTTP heartbeat, AI
  statistics, or a WebSocket `detections`, `heartbeat` or `frame` from the AI. While real, its mock
  detections, heartbeats, statistics and incidents stop (the generator checks this at least every
  2 s, the 10 Hz loop on every tick), mock statistics never overwrite an AI window, and
  «Симулировать инцидент» answers 409.
- AI stopped: the camera turns offline after `heartbeat_timeout_sec` (15 s) and mocks resume 60 s
  after the last real signal. A restarted backend re-derives "real" from the stored last heartbeat.
- cam-3 and cam-4 have no AI and keep their mocks all the time (DECISIONS.md I-007).
- Turning demo mode off stops all mocks; real AI data never depends on demo mode.
- `GET /api/v1/demo` (Bearer token) lists `active_camera_ids` (mocks running) and
  `real_camera_ids`. The incident journal has a source filter «Все источники» / «Внешний
  ИИ-модуль» / «Демо-генератор» / «Вручную» (`GET /api/v1/incidents?source=ai`).

## 7. API key seeding

- `make init` writes the same random 32-character value to `SEED_AI_API_KEY` and
  `SAFETY_AI_API_KEY`.
- On every backend start the seed makes the only non-revoked key named `ai-module` have exactly the
  hash of `SEED_AI_API_KEY` (unsalted SHA-256): it adds the key when missing and revokes other
  `ai-module` keys, logging `AI API key seeded from environment` when it changed something.
  Rotation: `python scripts/init_env.py --rotate`, then restart (`make dev`) — both sides read the
  new value.
- With `SEED_AI_API_KEY` empty a random key `ot_<token>` is created once (only when no active
  `ai-module` key exists), printed once as `AI module API key (shown once, saved to …): …` and
  written to `website/.secrets/ai_api_key` (git-ignored).
- Keys created by hand in Настройки → API-ключи also work; the key is never logged by either side.
- `make doctor` calls `GET /api/v1/ingest/config` with the key and fails on 401.

## 8. Adding a camera

1. **Website card.** Add the id to `AI_CAMERAS` in the root `.env` (for example
   `AI_CAMERAS=cam-1,cam-2,cam-5`) and restart: the seed creates «Камера cam-5», AI-enabled,
   `stream_type: mjpeg`, `stream_url: <AI_MJPEG_BASE_URL>/stream/cam-5.mjpeg`, without zones
   (existing cameras are never modified). Ids match `[A-Za-z0-9][A-Za-z0-9_.:-]{0,35}`. A camera
   created in «Камеры → Добавить камеру» gets a generated UUID instead; copy it with «Скопировать
   camera_id» and use it as the AI camera id, with stream type MJPEG and the AI URL, «ИИ
   анализирует» on.
2. **Zones.** Draw them in the zone editor (Камеры → camera → Зоны) and save.
3. **AI config entry.** Add the camera to `safety-ai/configs/demo_integration.yaml`:

   ```yaml
     - id: cam-5
       source: rtsp://user:password@192.168.1.20/live   # file, image directory, webcam index or URL
       timezone: ${TZ:-Asia/Yekaterinburg}
   ```

   Without `source:` the AI uses the card's `stream_url` from the website configuration, except
   when it points at the AI's own MJPEG (the camera is then marked failed, D-041).
4. `make restart-ai`, then `make demo-preset` to point the cards of all `AI_CAMERAS` at the MJPEG
   (needed when `AI_MJPEG_BASE_URL` changed after the cards were created).

## 9. Switching cam-1 to the webcam

The webcam variant is in `safety-ai/configs/demo_integration.yaml`, commented:

```yaml
  - id: cam-1
    source: data/samples/cam1.mp4
    # A live webcam instead of the demo video: replace the source line above with
    # source: 0
```

Replace `source: data/samples/cam1.mp4` with `source: 0` (webcam index 0) and run
`make restart-ai`. The equivalent one-line switch without editing the YAML is
`SAFETY_AI_CAMERAS__0__SOURCE=0` at the end of the root `.env` (cam-1 is the first camera), again
followed by `make restart-ai`; removing the line switches back. DEMO_SCRIPT.md uses the `.env`
line because `make doctor` checks the video files named in the YAML and reports a FAIL for
`source: 0` (DECISIONS.md I-014). The webcam works with `make dev` or the manual mode, not inside
Docker.

## 10. Model selection through the registry

The AI configuration names models, never weight files: `models.ppe`, `models.pose: pose_n`,
`models.vehicle: same_as_ppe`. `safety-ai/models/registry.json` lists every model (role, path,
class map onto the unified taxonomy, sha256, exports). A name resolves in this order:

1. an exact entry name (`ppe_n_sh17`, `pose_n`, `ppe_cppe_n_20261104_r1`);
2. an explicit alias listed in one entry's `aliases` (unique across the registry), such as
   `ppe_cppe_latest`;
3. computed aliases `<role>_<variant>_latest` / `<role>_latest`: the newest `created_at` among the
   entries of that role (and size variant) that are not marked `exclude_from_latest`.

The demo configuration selects `models.ppe: ppe_cppe_latest`, the explicit alias of the
Construction-PPE model `ppe_cppe_n_20261104_r1` (YOLO26n trained on the 12 official
Construction-PPE classes, stopped early at the deadline). The Construction-PPE entries are marked
`exclude_from_latest`, so `ppe_n_latest` still resolves to the SH17 nano model `ppe_n_sh17`; it
remains the fallback with one config line:

```yaml
models:
  ppe: ppe_n_latest
```

or `SAFETY_AI_MODELS__PPE=ppe_n_latest` in the root `.env`, followed by `make restart-ai`.
`make doctor` prints what the alias resolves to (row "registry alias of demo_integration.yaml").
A name that does not resolve marks the cameras failed with
`the models cannot be loaded: model '<name>' is not in models/registry.json; available: …` in
`/health` and the log. The PPE codes the loaded model can detect reach the website as
`extra.supported_ppe` with every heartbeat; the zone editor marks the others «не детектируется
текущей моделью». `same_as_ppe` loads the separate COCO vehicle model `vehicle_n` only when the PPE
model has no vehicle class (`forklift` is one).
